# Revise the topic pages from their queues

`/add-paper`, `/paper-audit` and `/research-question` don't rewrite topic pages for every paper: they queue each contribution in `<library>/topics/_queue/<page>.md`. Only a maintainer's `/add-paper` or `/paper-audit` run revises a page, and only once its queue reaches 10 items or 3 weeks; members' runs only queue. This skill clears the queues on demand, page by page, plus the queued note updates. The revision procedure itself is the one in `/add-paper` (section 3 step 3, "To revise", and step 3a), not a copy of it here, so the two never drift apart.

## 0. Who may run it

**Any lab member.** A *maintainer* is someone with push access to the library (`gh api repos/MonashUniversity-ShockLab/Library_of_Shock_Lab --jq .permissions.push` prints `true`) or whose own `CLAUDE.md` says they are a library maintainer; everyone else is a *member*. If unsure, treat the user as a member. The differences:

- **How the run lands.** A member always works on a branch and ends with a pull request, which the org's PR agent reviews and merges. A maintainer may commit on `main` and push, or use a branch with `--pr`.
- **How much.** A member's run revises at most **3 pages** by default, so the pull request stays small and fits one usage window; a maintainer's does every page with anything queued. `N pages` overrides either.

Two runs never work on the same page or note, because each one is **claimed** on Market before it is touched (section 1). Claims need Market: if it isn't reachable, a member's run stops (say so; nothing can be claimed). A maintainer's run may go ahead only if the user agrees, after being told that someone else might revise the same pages; an unattended run stops.

## 1. Setup

- **`<library>`** is the path in `SHOCKLAB_KNOWLEDGE` (the clone of `MonashUniversity-ShockLab/Library_of_Shock_Lab`): the folder with `SCHEMA.md`, `paper_notes/`, `topics/` and `tools/`. Resolve it once and use the absolute path. `library.py` means `python <library>/tools/library.py`.
- **Claims.** `paper_claim.py` means `python <library>/tools/paper_claim.py`. It finds Market itself (`SHOCKLAB_MARKET_PAPERS`, else the one mounted drive with `Library_of_Shock_Lab/papers`) and gets the user's GitHub login from `gh` (or pass `--as <login>`). Topic pages are claimed with `--topic <page>`, notes with `--audit <key>` (the same claim `/paper-audit` takes, so an audit and a note update never edit one note at once). Every `claim` passes `--branch <the run's branch>`. If `paper_claim.py --help` doesn't mention `--topic`, the clone is out of date: pull (below) and check again; if it still doesn't, stop and say the library's claim tool needs updating first.
- **`<add-paper>`** is the add-paper skill's `SKILL.md`: in the folder next to this skill's own (this skill's base directory, with `update-topics` replaced by `add-paper`). Give its absolute path in every subagent brief.
- **`<personal>`**: `SHOCKLAB_PERSONAL` if set, else `<library>/../My_Knowledgebase` if it exists, else `<library>` (as add-paper says). The progress file is `<personal>/Misc/update_topics.progress` (personal, never committed), lines `<kind>\t<name>\t<state>\t<commit or ->` where kind is `page` or `note` and state is `in-progress`, `done` or `released`; one run at a time.
- **Say what it costs before starting** (skip this when the run is unattended and the user approved it when scheduling): each page revision costs about as much as writing a paper note. Show the plan (step 2's list, with queue sizes and claim states) and ask how many pages to do, defaulting to 3 for a member and all for a maintainer.

**Pull first.** `git -C <library> switch main` and `git -C <library> pull --ff-only` (if the switch is refused because of uncommitted changes, show them and ask; an earlier run may have left the clone on its pull-request branch). Claim states are read against this clone, so it must be on an up-to-date `main` before section 2: only then does `done` mean the revision has merged. A member, a maintainer with `--pr`, and every unattended (scheduled overnight) run create a branch now, `update-topics/<github-login>-YYYY-MM-DD`, and put every commit on it; it ends in a pull request. A maintainer otherwise commits on `main` and pushes at the end.

## 2. Resume, then choose the pages

1. **Resume a cut-off run.** Read the progress file. A page marked `in-progress` was cut off mid-revision by this user's own earlier run. Its uncommitted changes to the page and its queue file are that run's half-done revision: discard both (`git -C <library> restore -- topics/<page>.md topics/_queue/<page>.md`; the queue sections come back with it) and put the page first in this run's list (its claim is still this user's: `mine`). Only ever discard a page the progress file marks `in-progress`. A note marked `in-progress` is handled the same way in section 4.
2. **Tidy this user's old claims.** `paper_claim.py list --topic` and `paper_claim.py list --audit`. A `done` topic claim (the page has been revised since) can be released (`paper_claim.py release --topic <page>`). For a `mine` claim from an earlier run whose pull request has since merged (`gh pr list --repo MonashUniversity-ShockLab/Library_of_Shock_Lab --state merged --head <its branch>`), release it; while its pull request is still open, keep it, and leave that page or note out of this run.
3. **Leave alone** any topic page or queue file with uncommitted changes the progress file doesn't explain (someone is editing it), any page changed in an open pull request to the library (`gh pr list --repo MonashUniversity-ShockLab/Library_of_Shock_Lab --state open --json number,files`), and any page whose topic claim is `taken` (someone else is revising it: name them and how long ago) or `stale` (claimed more than 14 days ago: suggest asking the claimant; take it over with `--take-over` only on the user's yes). Say which pages were left and why.
4. **The list.** If the user named pages, those (if they have anything queued; a page with an empty queue is skipped and said so). Otherwise every page with queued contributions (`library.py topics`, `queued` column, or the "Topic contributions queued" line of `library.py check`), in this order: pages with a major correction queued (`library.py check` lists them; a `**major.**` heading in the queue file), then the largest queue, then the oldest item. Cap it at the run's page count (section 0). Never create a topic page or revive one listed under "Retired topic names" in `SCHEMA.md`; a queue file for a retired page is reported, not revised.

## 3. Revise, one page per subagent

At most 2 page subagents run at once, and never two on the same page. For each page:

1. **Claim it:** `paper_claim.py claim --topic <page> --branch <branch>`. Only `claimed` or `already-mine` goes ahead. If the result is `taken` (someone claimed it a moment ago), drop the page, say who has it, and take the next page in the list instead.
2. Write `page\t<page>\tin-progress\t-` to the progress file.
3. Launch one `general-purpose` subagent with `effort: "high"`. Its brief: "Revise the topic page `<library>/topics/<page>.md` from its queue file `<library>/topics/_queue/<page>.md`. Read `<add-paper>` section 3 step 3 ('To revise') and follow it exactly, and read `<library>/SCHEMA.md` (topic page template and the guidance on length) and the library's `CLAUDE.md`. Work only the queue sections that exist now, delete exactly those from the queue file (delete the file if it is then empty) and leave any others. Edit only that page and its queue file; read notes as needed but don't edit them. Don't commit, don't ask anything. If the page would grow well past about 5,000 words, keep the content and say which thread should become its own page. Reply in at most 12 lines: contributions worked in, claims corrected (was / now), contributions rejected and why, word count before → after, and any split suggestion."
4. When it returns, check the diff is limited to the page and its queue file (`git -C <library> diff --stat`). Then commit just those two paths by name: `Revise topic page: <page>` (never `git add -A` or `.`). Mark the page `done` in the progress file with the commit hash. **Keep the claim**: it turns `done` by itself once the revision reaches `main` (the page's "Last updated" date passes the claim), and until then it stops anyone else revising the page under this run's open pull request.
5. **If a page is dropped** before its commit (the user stops it, the subagent fails), restore it as in step 2.1, release its claim (`paper_claim.py release --topic <page>`) and mark it `released`.
6. **Stop starting new pages** once any of these holds: the page cap is reached, the session has been compacted during this run, or you judge the context is past about 200k. Let a running subagent finish and commit its page. If the usage limit cuts the run off, the next run resumes from step 2.1.

After the pages, `library.py build` and `library.py check`; fix ERRORs and commit any rebuild (`INDEX.md`, `references.bib`).

## 4. Queued note updates

Unless `--no-notes`, apply the notes queued in `<library>/paper_notes/_queue/notes_to_update.md`, following `<add-paper>` section 3 step 3a exactly (with `--notes-only`, do this and skip sections 2.4 and 3). A member's run does at most 6 notes by default; a maintainer's does them all.

1. **Claim each note first:** `paper_claim.py claim --audit <key> --branch <branch>`. Skip a note that is `taken` (an audit or another run is on it; say who) or `stale` (as for pages), and any note in `<library>/paper_notes/_audit/` or with uncommitted changes. Write `note\t<key>\tin-progress\t-` to the progress file.
2. Work in batches of about 6 notes, one `high` subagent per note that needs a PDF, at most 2 at once, never on a note another subagent is editing. After each batch: delete exactly the finished notes' sections from the queue file (keep sections added since, and items the agent left), `library.py build` and `check`, and commit those notes with the file by name: `Apply queued note updates: <n> notes`. Mark them `done` with the commit hash.
3. **Release the note claims** once the commits are on `main`: a maintainer straight after pushing to `main`; on a branch, once its pull request has merged (step 2.2 of the user's next run does this, since a note update doesn't set the `audited:` date that would make the claim `done`). Release at once any note dropped before its commit, after restoring it (`git -C <library> restore -- paper_notes/<key>.md`).

Same stopping rules as section 3.

## 5. Land it and report

- **Push.** Show the user `git -C <library> log --stat origin/main..HEAD` and ask before pushing (an unattended run has that approval from scheduling). On `main`: `git -C <library> pull --rebase` and push. On a branch: `git -C <library> fetch origin` and `git -C <library> rebase origin/main`. On a conflict in `INDEX.md` or `references.bib`, take either side and run `library.py build`; in a queue file, keep the other side's new sections and drop only the ones this run worked in; on a topic page or note, abort the rebase, push the branch as it is and say so in the pull request (unattended) or show the user (attended). Then `library.py build` and `check`, commit any rebuild, push the branch and open a pull request to `MonashUniversity-ShockLab/Library_of_Shock_Lab` with the report as the body; the PR agent merges it. Then put the clone back on `main` (`git -C <library> switch main` and `git -C <library> pull --ff-only`), so the next run, an overnight run and `/lit` start from merged work; the branch's changes leave the working tree until the pull request merges (git-ignored files such as the PDFs in `attachments/papers/` stay).
- **Claims after a push to `main`:** release this run's note claims, and its topic claims too (they are `done` already).
- **Clear the progress file** of `done` and `released` lines once the commits are pushed.
- **Report:** pages revised (contributions worked in, main corrections, words before → after, split suggestions), pages skipped and why (claimed by someone else, uncommitted edits, open pull request, retired, cut off), queue sizes left (`library.py topics`), notes updated and items skipped, the claims this user still holds and when they clear (on merge), the `check` result, and the commits or pull request link.

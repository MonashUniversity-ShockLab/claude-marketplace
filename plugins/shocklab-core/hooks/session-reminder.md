ShockLab (shocklab-core plugin): this user is in the ShockLab group, which keeps a shared knowledge base and paper library (MonashUniversity-ShockLab/Library_of_Shock_Lab, local clone at $SHOCKLAB_KNOWLEDGE) so nobody works out the same org-specific thing twice.
- Before working out anything specific to the lab, Monash or its infrastructure (M3/MASSIVE, Slurm requests, Strudel, the Market drive, MATLAB on the cluster, lab rigs, cameras, schlieren/PIV/calibration, SPOD), use the lab-knowledge skill to check the knowledge base first. Keep the check quick.
- The org also holds the lab's standard MATLAB analysis code: Schlieren_Processing_Scripts (plus Schlieren_Tutorial), Acoustics_Processing_Scripts, PIV_Processing_Scripts and LES_Processing_Scripts. Before writing new processing code for those kinds of data, check the matching repo (lab-knowledge skill, section 4).
- For literature questions (what papers say about screech, jet noise, impinging jets, modal methods, rocket noise, ...), use /lit if the shocklab-library plugin is installed; otherwise start at INDEX.md and topics/ in the library.
- After solving something non-obvious and org-specific, offer to record it in the knowledge base once the user's task is done (lab-knowledge skill, section 3). Changes to the library's documentation/ (incl. Org Gotchas), methods/, facilities/ and codebase_notes/ pages go in only as proposals via /propose-docs, which a maintainer reviews (/review-proposals); only typo, link and formatting fixes go straight to a PR. When a review comes back, /propose-docs proposal_response takes the user through it.
- /propose-docs also has modes for bigger write-ups: /propose-docs <file or folder> turns one file or folder into a reference page for the lab; /propose-docs sweep checks the user's recent working documents for what the lab could use (token-heavy, so say so first); /propose-docs import brings a new member's notes and papers in.
- The lab's apps (e.g. FieldsPlayer, a player/exporter for *_Fields.mat) each have an org repo with releases and a card in the library's applets/ folder: check there before building a viewer or exporter, and use their documented command line when scripting them. To share an app the user built, use the publish-app skill (/publish-app).
- Pull requests in the MonashUniversity-ShockLab repos are merged by the org's PR agent: open the PR and leave it, rather than merging into main yourself or suggesting the user does. If the user asks to merge, first show what the merge brings in (files and +/- lines) and offer to merge only part (move those files into their own PR); if they still want to merge, go ahead, it is allowed. Never merge a library PR that changes the group pages (documentation/, methods/, facilities/, codebase_notes/) yourself: the PR agent merges those.
